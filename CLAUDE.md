# CLAUDE.md — AI agent guide for AI Fleet

This file orients an AI coding agent working in this monorepo. Read it before
making changes.

## Start here: read the code map first

**Before exploring the source, read [`docs/code-graph/index.md`](./docs/code-graph/index.md).**

It is an auto-generated structural map of the whole codebase — every function,
class, and test grouped into communities, with `file:line` locations and the
key execution flows (ranked by criticality). Use it to locate the right module
*before* opening files, instead of reading the tree top-to-bottom. Each
community links to its own page (e.g. `src-auth.md`, `agent-model.md`,
`views-render.md`, `src-token.md`).

The map is generated by [`code-review-graph`](https://github.com/tirth8205/code-review-graph)
(Tree-sitter → SQLite graph) and is kept in sync with the code by a pre-commit
hook (see below). If it looks stale, regenerate it:

```bash
npm run docs:code     # rebuild the graph + docs/code-graph/
```

> The docs are the *map*, not the *territory* — they can be up to one commit
> behind on a machine without the hook installed. Trust the source when they
> disagree, then regenerate.

## Querying the code — use the graphs before grep

Two complementary graphs index this repo. Prefer them over reading whole files
or grepping; fall back in this order (fewest tokens / most precise first):

1. **code-review-graph (CRG) — precise symbol lookup.** SQLite structural graph
   of functions/classes/tests with `CALLS`/`IMPORTS` edges + full-text search.
   Best for *"where is X"*, *"who calls X"*, *"what breaks if I change X"*.
2. **graphify — broad architectural exploration (on a CRG miss).** AST knowledge
   graph with community clustering across the whole repo. Best for *"what
   connects A to B"*, *"what's in this subsystem"*, multi-hop neighborhoods.
3. **grep / read — last resort.** Only for what the graphs don't index: config,
   logs, string literals, comments.

Both are **local, gitignored** indexes. Build/refresh them (they also refresh
automatically in the background after each commit — see `.githooks/post-commit`):

```bash
npm run graph:build     # builds .code-review-graph/graph.db  AND  graphify-out/
```

### Query commands

**CRG (structural).** If the CRG MCP server is installed, use its tools
(`semantic_search_nodes_tool`, `query_graph_tool`, `get_impact_radius_tool`, …).
Otherwise query the SQLite graph directly:

```bash
DB=.code-review-graph/graph.db
# where is a symbol defined?
sqlite3 -box "$DB" "SELECT kind,name,file_path,line_start||'-'||line_end AS lines
                    FROM nodes WHERE name='<Symbol>';"
# who calls it?
sqlite3 -box "$DB" "SELECT DISTINCT source_qualified,line FROM edges
                    WHERE kind='CALLS' AND target_qualified LIKE '%<Symbol>%';"
```

**graphify (architectural).** CLI over `graphify-out/graph.json`:

```bash
graphify query "what connects gateway auth to the org service" --budget 800
graphify path "<NodeA>" "<NodeB>"     # shortest path between two nodes
graphify explain "<Symbol>"           # plain-language node + neighbors
```

The committed, human-readable CRG map is `docs/code-graph/index.md` (read that
first for orientation). graphify's community report is
`graphify-out/GRAPH_REPORT.md` (local, regenerated by `npm run graph:build`).

## What this is

**AI Fleet** — a microservice-decomposed tool to manage Linear projects and run
isolated planner + coder deep-agent services over a shared library. npm
workspaces: `packages/*` (shared libs, CLI) and `services/*` (gateway, planner,
coder, org, settings). Product docs and setup live in [`README.md`](./README.md).

## Commands

```bash
npm start              # run all services (scripts/start-all.js)
npm test               # node --test unit suites
npm run test:e2e       # Playwright end-to-end
npm run docs:code      # regenerate the code-graph docs (docs/code-graph/)
npm run hooks:install  # enable the repo git hooks (core.hooksPath=.githooks)
```

Per-service guides live alongside the service (e.g.
[`services/org/CLAUDE.md`](./services/org/CLAUDE.md)) — read the relevant one
before changing that service.

## Keeping the code map fresh (pre-commit gate)

`.githooks/pre-commit` regenerates `docs/code-graph/` and **blocks the commit**
if the result differs from what you staged, so the map never drifts from the
code. It runs only when a commit touches source in a language code-review-graph
supports (`.py`, `.ts`, `.go`, `.rs`, `.java`, `.tf`, … — the full `CODE_RE`
list in `.githooks/pre-commit`) or the docs themselves.

- Enable once per clone: `npm run hooks:install`
- On a block: `git add -A docs/code-graph` and commit again.
- Emergency bypass: `SKIP_DOCS_HOOK=1 git commit …`
- Requires the CLI: `pipx install code-review-graph`.

See [`.githooks/README.md`](./.githooks/README.md) for details.
